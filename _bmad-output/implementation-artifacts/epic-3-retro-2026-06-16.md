## Challenges & Learnings

- **Story 3.3 complexity underestimated** — 10 review patches was the highest in Epic 3. The combination of 7 VoteButton states + 5 HorseSelectCard states + optimistic update + mobile responsiveness created high state-complexity.
- **Cross-story API contract gap** — `race_horse_id` was missing from the `GET /api/v1/races/{id}` response schema in Story 3.2, blocking Story 3.3 frontend implementation. Should have been caught during Story 3.2's review.
- **Bare `catch` blocks reappeared** — Story 3.5 review caught them, despite the project-context rule. This pattern kept slipping through without automated checks.
- **Frontend vitest deferred again** — From Epic 1 → Epic 2 → Epic 3, frontend automated testing remains unconfigured.

## Key Insights

1. **Complex stories need front-loaded design** — Story 3.3's 10 patches show that multi-state interactive components benefit from a more detailed UX/state spec upfront.
2. **Cross-story dependency validation needs a process** — API contract gaps between Story 3.2 and 3.3 suggest a "dependency checker" step before starting a story that relies on a previous story's API.
3. **Pattern enforcement without automation is leaky** — Bare catch blocks kept slipping through despite project-context rules. Consider adding lint rules.
4. **Test infrastructure confidence is high** — 179 tests, zero regression, scoring engine 100% branch coverage. This enabled confident refactoring and extension.
